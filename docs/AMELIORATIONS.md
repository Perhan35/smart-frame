# SmartFrame — Plan d'amélioration (à traiter point par point)

**Date :** 2026-11-08
**Base :** tout le dépôt (`main.py`, `modes/`, `scripts/`, service systemd, README, config).
**Hypothèses retenues :**

- Le cadre doit rester sûr même sur un réseau local **non fiable** (Wi-Fi partagé, objets connectés). Les points réseau (MQTT, TLS) sont donc prioritaires.
- Pour l'audio, on vise à la fois un chiffre dBA fiable dans Home Assistant **et** un joli visuel à l'écran.

Ce fichier **fusionne** la revue détaillée [CODE_REVIEW.md](CODE_REVIEW.md) (réf. `SEC-x`, `A-x`, `Q-x`, `DSP-x`, `EFF-x`, solutions `R-x`) et les **nouveaux points** trouvés dans cette analyse (réf. `N-xx`, détaillés en bas de page). Les points ouverts de CODE_REVIEW.md sont suivis ici, via la colonne **Statut**.

## Par où commencer

1. **#1 N-02** : un seul message MQTT invalide coupe MQTT pour de bon (5 min de travail).
2. **#2 Q-1** : des « races » entre threads peuvent faire planter tout l'orchestrateur.
3. **#3 N-01** : en passant de `audio` à `off`, l'état se bloque sur `audio`.
4. **#4 SEC-3** : MQTT en clair, mot de passe optionnel.
5. **#5 SEC-1** : le service dépend de `sudo` sans mot de passe (tout bug devient « root »).
6. Puis les **P1 audio** (#17 à #24), qui rendent le chiffre dBA dans HA cohérent.

## Détails des nouveaux points (N-xx)

Les points `SEC/A/Q/DSP/EFF` sont expliqués en détail dans [CODE_REVIEW.md](CODE_REVIEW.md). Voici les explications des nouveaux.

### N-01 — L'état se bloque sur `audio` après un passage en `off` (#3)

1. `start_mode("off")` met `current_mode = "off"` puis tue `audio_mode.py`.
2. `audio_mode.py` ne supprime **jamais** `/tmp/smartframe_dba`, qui a été écrit il y a moins d'1 s.
3. Pendant les ~5 s suivantes, la boucle « guardian » ([main.py:1381-1391](../main.py#L1381-L1391)) voit « état off + bridge frais » et remet `current_mode = "audio"`.
4. HA affiche `audio`, l'écran est éteint et aucun process ne tourne. Choisir `audio` dans HA ne fait rien, à cause du `if mode == current_mode: return` ([main.py:938](../main.py#L938)). `AudioMonitor` reste coincé dans sa branche « audio mode actif », donc le capteur dBA ne publie plus rien.

**Comment le vérifier :** chercher `GUARDIAN: Audio bridge active but state is 'off'` dans `journalctl -u smartframe` après un passage audio → off.

### N-02 — Un octet invalide coupe MQTT pour de bon (#1)

Dans paho 2.1.0 (vérifié dans `.venv`), une exception levée dans `on_message` est **relancée** (`suppress_exceptions = False` par défaut). Elle sort de `loop_forever()`, le thread réseau s'arrête et rien ne le relance. Le process continue de tourner mais n'écoute plus MQTT, et le broker publie le LWT `offline` après le keepalive. Il suffit de publier un payload comme `\xff` sur `smartframe/set_mode`. Sur un réseau partagé où l'auth MQTT est optionnelle, c'est à la portée de n'importe qui.

**Pire si le message est publié en `retain` :** le broker le renvoie à chaque reconnexion et à chaque redémarrage du service, donc MQTT meurt aussitôt à chaque fois. Redémarrer ne suffit pas. Il faut effacer le message retenu en publiant un payload vide en `retain` (ex. `mosquitto_pub -t smartframe/set_mode -r -n`).

### N-03 — `device_index` de la config ignoré (#7)

`_discover_audio_device()` ne lit jamais `config.audio.device_index`. Son résultat est passé à `audio_mode.py` via `SMARTFRAME_AUDIO_DEVICE`, qui **écrase** la valeur lue dans la config ([audio_mode.py:33-35](../modes/audio_mode.py#L33-L35)). `AudioMonitor` utilise aussi uniquement l'auto-détection.

### N-05 — Course au démarrage écran OFF / ON (#8)

[main.py:1320](../main.py#L1320) lance `set_display_power(False)` dans un thread. Si `default_mode` vaut `mirror` ou `audio`, le worker lance en même temps `set_display_power(True)` ([main.py:964-966](../main.py#L964-L966)). Les deux envoient des commandes DDC sur le même bus I²C dans un ordre imprévisible, et modifient tous les deux la liste `_working_methods["hardware"]` (`.remove()` peut lever `ValueError`).

### N-07 — `update_config.py` efface des clés valides (#9)

`main.py` lit `brightness_topic`, `brightness_state_topic`, `contrast_topic`, `contrast_state_topic`, `color_preset_topic`, `color_preset_state_topic`, `input_source_topic` et `input_source_state_topic`, mais ces clés ne figurent pas dans `config.example.yaml`. Si un utilisateur les ajoute, `deep_prune` les supprime au prochain `git pull`.

### N-09 — Moyenne stéréo : −6 dB (#19)

L'INMP441 avec L/R relié à GND n'envoie du son que dans le créneau **gauche**. Si le périphérique ALSA annonce 2 canaux (probable avec `googlevoicehat-soundcard`), `audio_mode.py` fait `mean(axis=1)` : (signal + 0) / 2, soit −6 dB. **À vérifier sur le Pi :** `arecord -l`, puis le `maxInputChannels` affiché dans les logs « Opening stream: N channel(s) ».

### N-11 — 1 échantillon par seconde ≠ niveau de la seconde (#20)

Le capteur HA reçoit la valeur instantanée du niveau rapide au moment de l'envoi. Un claquement de porte de 200 ms entre deux envois est invisible. La norme pour un suivi dans le temps est le **LAeq** : moyenne de l'énergie (pas des dB) sur l'intervalle. On peut ajouter **LAmax** pour les pics.

### N-13 — Offset de calibration théorique (#40)

La fiche technique de l'INMP441 indique une sensibilité de −26 dBFS pour 94 dB SPL (sinus à 1 kHz). En int16 cadré à gauche, un sinus à −26 dBFS a un RMS d'environ 1 160 LSB, soit ~61 dB dans l'échelle du code. L'offset théorique est donc d'environ **94 − 61 ≈ +33 dB**. À confirmer avec un sonomètre ou une appli, car la chaîne ALSA peut changer l'échelle.

### N-16 — Surface alpha plein écran (#26)

`overlay_surface` (1920×1080, `SRCALPHA`) est vidée puis fusionnée sur l'écran à chaque image. Le fond est noir et les barres ne se chevauchent pas, donc `couleur × alpha / 255` dessiné en opaque donne le même rendu, sans aucune fusion. **À mesurer :** temps par image avant / après (`time.perf_counter()` autour du dessin).

### N-19 — Variables SDL définies trop tard (#38)

`pygame.display.init()` est appelé ligne 67, et `SDL_VIDEODRIVER` ne l'est que ligne 73. Le pilote vidéo est choisi à l'`init()`, donc `kmsdrm` n'est jamais appliqué. Le repli `dummy` rappelle `init()` sans `quit()` avant, ce qui ne fait rien. `SDL_HINT_RENDER_DRIVER`, `SDL_HINT_RENDER_SCALE_QUALITY` et `SDL_VIDEO_GLES2` ne sont pas des variables lues par SDL : les vraies s'écrivent sans `HINT_`. En revanche, `SDL_RENDER_DRIVER` est défini avant `set_mode()`, et sous Wayland SDL2 peut s'en servir pour la surface d'affichage. **Il faut donc le garder**, et vérifier son effet sur le Pi.

### N-39 — Plantage possible au démarrage, pendant l'ouverture du micro (#75)

Pendant les tests sur Mac de cette session, `main.py` a planté 2 fois (segfault) entre les lignes de log « Using the system default audio input » et « Monitor: microphone open ». À ce moment-là, 2 threads utilisent PortAudio en même temps. Le thread lancé au démarrage pour chercher le micro crée puis ferme sa propre instance PortAudio (`pyaudio.PyAudio()` puis `terminate()`), pendant qu'`AudioMonitor` ouvre la sienne. PortAudio ne supporte pas bien ce genre d'accès en parallèle. Les 8 essais suivants n'ont pas planté, et l'ancien code a le même enchaînement : c'est donc une hypothèse, à surveiller sur le Pi. Comme systemd relance le service (`Restart=on-failure`), un plantage ne se voit que dans le journal.
